# Two-factor authentication

Optimus supports one TOTP authenticator for the installation, in addition to `OPTIMUS_ACCESS_KEY`. The name field is a display name, not a separate account. Ente Auth, Google Authenticator, and other standard TOTP apps work without a paid service. Verification runs locally.

## Enable

1. Log in and select **Security** in the left sidebar (the navigation moves above the page on smaller screens).
2. Confirm your access key and select **Set up two-factor authentication**.
3. Scan the QR code with your authenticator, or manually add the setup key as a time-based, six-digit SHA-1 token with a 30-second period.
4. Enter the current six-digit code and select **Verify and enable** within ten minutes.
5. Download the ten recovery codes and store them securely, preferably away from the device running Optimus. They are displayed only once.

Setup does not protect login until the confirmation code succeeds. Confirmation is bound to the browser session that started setup. Enabling or disabling signs out other browser sessions. The current session stays signed in.

On subsequent logins, enter your name and access key, then the authenticator code. An unused recovery code can replace the authenticator code; the access key is still required. Each recovery code works once. Security shows the number remaining. To obtain a fresh set, disable 2FA with your access key and a valid authenticator/recovery code, then set it up again.

## Verification and storage

- Six-digit TOTP codes rotate every 30 seconds. Verification accepts the previous, current, or next interval to allow small clock differences. Keep the host and phone clocks synchronized.
- Successful codes are consumed atomically. A used interval or any older interval cannot be used again, including immediately after setup. Wait for the next code if needed.
- Ten failed authentication attempts in a five-minute window temporarily block login and security changes until that window expires. The limit is shared across the installation and persists across backend restarts. Valid access-key submissions that still require a second factor do not clear failures.
- Postgres `app_data.auth_security` holds a versioned Fernet-encrypted document, including the secret, pending setup, used interval, recovery-code SHA-256 hashes, and failure counters. Updates use a transaction and advisory lock across workers.
- `data/.auth.key` is created with mode `0600` on the first authentication/security request. It is excluded from Git and application backup ZIPs. All workers must share the database and key. Missing, incorrect, or corrupt keys fail closed when a security document already exists.
- QR codes are generated by the backend and embedded directly in the page. No external QR service receives the secret. Secrets and recovery codes are not stored in browser local storage.

The existing browser sessions remain in backend memory; restarting the backend signs them out. When accessing Optimus beyond localhost, serve it over HTTPS. TOTP does not change API-key authentication for public ingestion endpoints. Protect those keys separately.

## Backup and recovery

Application backup/restore ZIPs deliberately exclude authentication state and its encryption key. Restoring tool data preserves the installation's current 2FA configuration, failure counters, and consumed recovery codes.

For a full installation migration, transfer the database and the original `data/.auth.key` securely. A database-only restore without that key locks authentication. Restoring an old full database snapshot also restores its old recovery-code usage and replay counters; after such a restore, disable and re-enroll 2FA to replace the old secret and codes.

If the phone is unavailable, log in using an unused recovery code. If the encryption key is missing, restore the original key file; recovery codes cannot decrypt the database.

If both the authenticator and recovery options are lost, a trusted operator with host/database access can reset this installation's authentication state:

1. Stop every Optimus backend process so all browser sessions are cleared.
2. In the Optimus database, execute `DELETE FROM app_data WHERE key = 'auth_security';`.
3. Keep an existing valid `data/.auth.key`. If it was lost or damaged, remove the damaged file while the backend is stopped; a new key will be created on the next login.
4. Restart, sign in with the access key, and enroll 2FA again immediately.

This operator procedure removes 2FA and authentication attempt counters. Never expose database or host access to untrusted users. No automatic reset endpoint is provided.
